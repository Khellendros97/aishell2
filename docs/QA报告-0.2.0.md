## 五、缺陷清单

### QA-01【严重，已修复 2026-08-09】AI 工作模式在生产服务器自动执行远程命令，全程无人工确认
- 复现：AI 模式=「工作」，审批=smart；附终端快照提问。
- 实际:AI 自主执行约 12 条远程命令，全部自动放行，操作卡片事后展示。其中一条命令尝试 `mysql -uroot -p'$(grep -oP "(?<=password=).*" .../rad_db_setup.conf)'`,即从配置文件提取密码的模式。命令本身均只读，未造成损害。
- 风险：一线员工权限大、经验少，难以判断 AI 命令是否安全；现有「AI 远程操作锁定」开关藏在服务器卡片上，默认未锁。
- **整改（三重兜底，均已上线并通过门禁与端到端验证）**:
  1. **意图层（提示词）**:agent/yolo 系统提示新增「凭据纪律」——不得主动查找/读取/提取凭据，任务确需凭据时停止并请用户手动执行；见到「***已脱敏***」不得用 base64/hex/分段读取绕过。(ai.rs SYSTEM_PROMPT_AGENT)
  2. **门禁层（智能审批前置规则）**：确定性正则规则先于 LLM 判定，命中即转人工（offline、零误放行、不消耗判定请求）。覆盖三类:① 凭据文件（rad_db_setup.conf、redis_acl.conf、my.cnf、.env、shadow、id_rsa、ssl.key 等 + etc/srun.conf、etc/system.conf 路径锚定）;② 命令替换注入凭据（`$(...password...)`);③ 检索工具+凭据关键词（grep/sed/strings+password/secret/token 等）。普通 `cat xx.conf` 不拦，避免审批疲劳。同时给 LLM 判定提示词补了凭据条目作为二道防线。拦截理由透传前端，人工审批卡展示「智能审批拦截（转人工确认）:…」。(smart_approval.rs precheck_credential_access;ai.rs/ai.ts 事件与卡片)
  3. **数据层（输出脱敏）**：新增 redact 模块，在写入 LLM 上下文与落盘前脱敏：KV 形态（password/pwd/secret/token/api_key/requirepass 等键的引号/裸值/JSON/YAML/redis 空格形态）+ keyring 已知密钥字面量（服务器密码、LLM/Brave Key)+ 值收集（会话级收集 KV 值，掩盖 `-p'值'`、正文复述、动作摘要等裸文本形态）。覆盖四个通道:run_command 输出（截断前）、ai_chat prompt、session_upsert 落盘、Store 加载时历史会话一次性迁移清洗。(redact.rs、ai.rs、store.rs)
- **端到端验证（2026-08-09，真实 30.37 环境）**:① `cat flow_log.conf` 智能放行，输出 `db_password="***已脱敏***"` 并附脱敏提示，AI 正确复述「密码已脱敏」;② 直接索要密码，AI 依凭据纪律拒绝并给出用户手动命令卡;③ `cat system.conf` 触发人工审批卡并显示拦截原因，批准后输出 `redis_password="***已脱敏***"`，全文无明文；④ 本机 aishell.json 历史明文（含动作摘要中的 `-p'Srun4000@…'`）经迁移+一次性清理后归零，重启后保持干净。
- **残留边界（已知、可接受）**:① 防「顺带泄露」不防恶意模型主动编码绕过（base64/xxd);② 脱敏计数含幂等重匹配，轻微偏高（仅展示用）;③ 历史动作卡折叠后不显示拦截理由（仅实时卡可见，AiActionRecord 未持久化 smartReason);④ QA-01 原始建议中的「生产标签默认锁定/首命令横幅/只读写入卡片区分」未纳入本次整改，建议单独立项。
- 原建议:① 服务器支持「生产」标签，生产机默认锁定 AI 远程操作；② 会话内首次远程执行给一次性横幅提示；③ 命令卡片区分「只读/写入」视觉样式；④ 对密码提取类命令模式强制人工确认。—— ④ 已由门禁层实现，①②③ 见上。


### QA-02【严重，已修复 2026-08-09】远程编辑器无外部变更检测，存在静默覆盖风险
- 复现:SFTP 打开 flow_log.conf 改为 14 并保存(生效)；随后在终端从备份恢复为 7。
- 实际：编辑器标签仍显示 14，无「文件已被外部修改」提示(此行为已验证)。此时再按 Ctrl+S 将覆盖终端侧的恢复(后果为推断，未执行)。
- **整改**：保存前远端属性校验。后端 `sftp_write` 新增可选 `expectedSize/expectedMtime`（编辑器打开时的 stat 快照），远端属性不一致时**不写入**，返回 `conflict=true` + 实际属性；写入成功后重新 stat 返回落盘后基线。前端编辑器记录打开时快照，保存命中冲突时：Ctrl+S 弹三选对话框（覆盖保存/重新加载/取消），自动保存与关闭不弹窗只提示一次且不覆盖外部修改；覆盖保存后以服务器返回基线重建，避免连环误报。(sftp.rs sftp_write+SftpWriteResult、editor.ts queueSave/conflictDialog、sftp.ts 打开时快照)
- **端到端验证（30.37 实测）**:建测试文件 → 外部追加一行 → 编辑器改值后 Ctrl+S → 弹窗显示「远端文件已被外部修改（当前大小 19 字节、修改时间 20:58:40）」→ 覆盖保存 → 服务器 mtime 20:56→21:04 真实写入 → 再次编辑保存无假冲突（toast「已保存到远端」）；测试文件已清理。

### QA-03【已撤销，非缺陷】SFTP 列表视图双击文件无反应
- 初判：自动化测试注入的两次双击(CDP `click({clickCount:2})` 与坐标双击）均未打开文件。
- 复核：2026-08-09 经人工手动双击验证，列表视图双击可正常打开编辑器；代码侧 tr 的 dblclick 绑定正确(sftp.ts:1481)。确认为自动化注入事件未触发 WebView2 的 dblclick 合成，属测试方法问题，产品行为正确。

### QA-04【一般，已修复 2026-08-09】多个同名终端标签不可区分
- 复现：对同一服务器开两个 SSH 终端。
- 实际：两个标签均显示「30.37」，无法分辨哪个在 tail -f。
- **整改**：① 同名终端自动编号——第二个同标题终端显示「30.37 #2」（编号不复用，取现有最大后缀+1）；② 终端标签右键菜单新增「重命名」（promptDialog 输入，会话级生效，含空名/路径分隔符校验）。「添加到对话」的服务器引用名随重命名联动。(core.ts uniqueTerminalTitle/renameTerminalTab)
- **端到端验证**：复制 SSH 渠道 → 新标签自动「30.37 #2」；右键重命名 → 输入「抓包终端」生效，标签栏实时更新；测试标签已关闭。

### QA-05【一般】AI 会话列表同名难辨认，且默认恢复旧会话
- 复现：会话下拉出现 4 个同名「终端快照」；进入工作台默认展开历史旧会话。
- 建议：快照类会话按首条问题/时间自动命名；或默认新建会话。

### QA-06【建议】历史命令卡片标题截断混乱
- 实际：长命令/多行命令的卡片标题显示为残片，如 `<.conf*; md5sum ...`。
- 建议：截断保留命令开头，而非中间撕裂。

### QA-07【建议】命令收藏「立即执行」无目标提示
- 实际：多终端打开时命令发至活动终端，但无任何提示发往了哪个终端。
- 建议:toast 提示「已在 30.37 终端执行」。

## 十一、数据库受管查询通道（db_query，2026-08-10 上线）

按「只读账号 + keyring 凭据 + 结构化 db_query + SQL 门禁」方案实现，覆盖 mysql/clickhouse/redis 三型：
- 入口：服务器列表 → 服务器卡片 →「数据库连接」按钮；连接配置（类型/名称/主机/端口/用户/密码/默认库/AI 可执行命令白名单），密码存 keyring（`db:<serverId>:<connId>`），默认只读命令集（SELECT/SHOW/DESC/EXPLAIN、redis GET/KEYS/SCAN 等）。
- AI 工具 `db_query(serverId, connectionId, command)`：list_servers 返回 connectionId 供发现；执行经 SSH 在服务器本机跑客户端（临时 defaults-file / config.xml 承载凭据，ps 不可见）；命令白名单 Rust 最终裁决，多语句分段校验（防 `SELECT 1; DROP x`）；写命令（用户加入白名单的 UPDATE 等）走人工审批。
- 端到端验证（30.37 实测）：MySQL 查询 online_radius=3 ✓；Redis SCAN 10 keys ✓；`UPDATE` 触发审批卡（读/写分类 + 智能审批拦截）→ 拒绝后未执行 ✓；全程无密码进入 LLM 上下文 ✓。
- 踩坑实录（实现期修复）：SSH set_env 被服务端忽略（AcceptEnv 默认空）→ 改 base64 内嵌；`--defaults-extra-file` 会被服务器 ~/.my.cnf 的 user=root 覆盖 → 改 `--defaults-file`；redis-cli 单 argv 多词被当作未知命令 → 按空白拆参。

## 十二、事故教训（与 QA-01 直接相关）

测试期间 AI 在「修复工具链」时经智能审批放行的 `cat > /usr/local/bin/redis-cli` 命令，因该路径是指向 `/srun3/redis/bin/redis-cli` 的符号链接，**穿透覆盖了生产 redis-cli 真二进制**（变成自我递归脚本），导致 386 个自旋进程、3 个 100% CPU 看门狗脚本、redis 客户端连接全线挂起；服务器端已恢复（真二进制从 8.0.4 源码树还原、僵尸清理、load 归 0.07）。
结论：AI 的「善意修复」在写路径上仍可能造成生产事故——进一步印证 QA-01 遗留建议的必要性：**生产服务器标签 + 默认锁定 AI 远程操作**（至少锁定 run_command 的写操作），应尽快单独立项实施。
